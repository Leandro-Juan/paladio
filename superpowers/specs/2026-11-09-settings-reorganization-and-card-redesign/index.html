    Design Specification: Settings Categories Reorganization, Tactical Card Redesign & Backend Persistence¶

    Date: 2026-11-09
    Author: Antigravity
    Status: Specification Complete — Pending User Review Before Implementation
    Canonical Spec Path: docs/superpowers/specs/2026-11-09-settings-reorganization-and-card-redesign.md

    1. Overview & Motivation¶

    The configuration workstation (/config) was recently extracted from a monolithic page into modular subcomponents, but the category taxonomy and card layouts still suffer from structural friction: 1. Asymmetric & Fragmented Taxonomy: Regional & Currency exists as an orphaned single-item category, while Language & Locales is placed under Workspace & Interface. Meanwhile, personal profile settings and administrative user provisioning are mixed together under Governance & Security. 2. Missing Travel & Engine Domain Representation: As a sovereign travel intelligence platform powered by LangGraph multi-agent swarms, deterministic C++20 combinatorial routing, and continuous ML taste learning, settings for solver constraints, map cartography, agent critic behaviors, units of measurement, and data vault backups have had no formal persistence layer or UI home. 3. Card Presentation Upgrade: Settings cards need to transition to a modern, tactile card archetype inspired by the user-provided reference design (clean outer cards, segmented sub-tab pills, nested tactical panels with rounded controls, toggle switches, and 3-dot contextual action menus) fully unified with Paladio's Pacific Jazz & Japanese Minimalist Tactical aesthetic. 4. Unified Backend Persistence: Both user-level travel preferences and instance-level system configurations must be persisted cleanly without mock fallbacks: - Personal travel settings (maps, units, solver_preferences) persist to UserModel.preferences (JSONB) via PATCH /users/me. - Instance/admin settings (engine, swarm, vault) persist to SystemConfigModel (system_config table) via typed GET/POST /system/settings/{domain} endpoints with strict Pydantic validation.

    4. Backend Implementation & API Design¶

    Pydantic Schemas (backend/app/schemas/settings.py)¶

    • EngineConfigPayload:
    • default_max_walking_km: float (1.0 to 50.0, default: 12.0)
    • pacing_tempo: str ("leisurely" | "balanced" | "intense", default: "balanced")
    • attraction_burnout_limit: int (default: 6)
    • deal_scraper_cadence_hours: int (default: 24)
    • price_alert_threshold_pct: float (default: 15.0)
    • SwarmConfigPayload:
    • critic_strictness: float (0.0 to 1.0, default: 0.75)
    • thinking_token_budget: int (default: 2048)
    • auto_ticket_ingestion: bool (default: true)
    • require_human_approval_on_repair: bool (default: false)
    • VaultConfigPayload:
    • auto_snapshot_enabled: bool (default: true)
    • snapshot_retention_days: int (default: 30)

    REST Endpoints (backend/app/api/system.py)¶

    • GET /system/settings/{domain}:
    • Fetches the validated domain configuration dictionary from SystemConfigModel.
    • Allowed domains: engine, swarm, vault.
    • POST /system/settings/{domain}:
    • Validates payload against the domain schema and writes directly to SystemConfigModel(key=domain, value=data).
    • Requires admin role for instance-wide parameters.

    User Preferences Model (backend/app/schemas/user.py)¶

    • Extends UserPreferences with map_preferences, units_preferences, and user_solver_overrides.
